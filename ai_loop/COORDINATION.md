# COORDINATION — 三者連携ボード

このファイルが、オーナー・Muse（リード）・Claude Code・Codex の
**唯一の連携窓口**です。人間がメッセージを中継しなくて済むよう、
状態・担当・質問はすべてここに集約します。git 経由の非同期連携です。

## 役割

## 運用ルール

1. **セッション開始時**: `git fetch` で最新の `ai-native` を取り込み、
   このファイルと `CLAIMS.md`、`BACKLOG.md` を読む。
2. **セッション終了時**: 下の状況ボードで**自分の行だけ**を更新し、
   自分のブランチへ push する（push できない環境では、更新内容を
   記録ファイルとしてリードへ渡す）。
3. **質問・相談**は下の「質問・相談」節に、宛先と日付つきで書く。
   回答も同節に追記する。チャットや口頭で済ませない（記録が正）。
4. **正式な決定**はオーナーの承認を経て、リードが `LEDGER.md` に
   反映した時点で確定する。このボードの記載は提案・状況の共有であり、
   決定そのものではない。
5. 担当や触るパスが衝突したら、作業を止めて質問節に書く。
   先に宣言した側（`CLAIMS.md`）が優先。
6. **リード判断の範囲**（2026-11-19 オーナー指示）: 承認済みフェーズ内の
   API 形状・実装順序・検証方法・小物の仕様は、オーナーへ上げずリードが
   判断する。フェーズの新設、外部公開、お金・アカウントに関わることは
   従来どおりオーナーの判断。
7. **判定の数値化**（2026-11-19、AI 開発効率化）: 新規 BACKLOG 項目の
   「判定」は、可能な限り数値・構造化出力・合否 JSON で書く。見た目の
   印象だけに頼る判定は GPU 確認待ちで滞留するため、指標（レポートの
   数値、差分、件数）に寄せる。印象確認が本質の項目は、その旨と確認者
   （オーナー／ローカル）を判定に明記する。
8. **プルリクエストは使わない**（2026-11-19 オーナー指示「このプロジェ
   クトにプルリクなんて要らない。全部どんどん反映していい」）: 検証済み
   ブランチはリードが直接 ai-native へ統合する。PR が作られていても、
   そのレビューを統合の前提にしない。完璧を待たずに反映し、ダメなら
   また修正する（イテレーション優先）方針とする。
9. **AI から呼び出される前提で設計し、エージェント能力に適応する**
   （2026-11-19 オーナー指示）: 全ての機能は AI エージェントが CLI／
   MCP／構造化出力で呼ぶ前提で設計する。エージェントごとに能力が違う
   （例: Codex は画像生成可、Claude Code は不可）ため、道具は能力の
   有無で使えなくならず、能力プロファイルに応じた代替ルートを返す。
   具体化は B-404。

### Q13（Claude Code ローカル → オーナー／リード、2026-11-18）一枚絵の 3D 化（U.ZU Picture）・画像からの PBR 生成・外部推定マップの取り込み
オーナーの依頼「一枚絵をパララックスで動かし、PBR にしてエフェクトとライトでかっこよくする仕組みを基本機能に」「操作するのは AI エージェント」「テクスチャ画像から PBR を作る」「画像から法線を推定させる口」を受けて、ローカル（Windows・RTX 4050）で GDScript の試作を作り、GPU で動作を確かめた。コードは `ai_loop/prototypes/picture/`（ブランチ `agent/picture-claude-local`）。絵は公開リポジトリなので入れていない。記録は `ai_loop/iterations/2026-11-18-PICTURE-claude-local.md`。

**できたこと（試作・すべて GPU で確認）**
1. **U.ZU Picture**: 絵＋深度（disparity／linear）＋任意の法線・マスクを JSON 1 枚で指定 → 起伏メッシュ（深度の段差で裂く＋裏に穴埋め済みの背景メッシュを置く多重パララックス）、描かれた光は EMISSION に残し、濡れた所だけ PBR にして本物のライトを足す。効果: 雨、火の粉、距離 4 段の霧の板（深度で柔らかく馴染む）、空の雲の流れ（2 層）、稲光（2 回の明滅＋方向ライト＋霧と空も光る）、揺れ（滝・葉・水面）、カメラのゆっくりした寄りと揺れ（端が見えないよう画角に余白）。ルックは UZULook＋UZUPostEffect を流用。
2. **エージェント向けの口**: 座標はすべて絵のピクセル。全コマンドが JSON 1 行（`UZU_RESULT`）を返す。`analyze`（光源候補を重ね描き画像つきで出す）→ `snap`（大まかな点を近くの一番明るい点へ寄せる）→ `adopt` → `validate` → `shot`（指定秒の PNG と、動きが一目で分かる motion.png）。
3. **画像から PBR**: 1 枚の写真 → albedo（陰影を弱める）／normal（OpenGL）／ORM／height／material.tres。種類（stone, brick, cobble, wood, metal など 10 種）ごとの強さは Poly Haven の実スキャンに合わせて決めた。`preview`（球＋床を斜めの光で GPU 撮影）と `compare`（実スキャンとの角度誤差）つき。
4. **外部推定マップの取り込み**: `map import` が、外のモデル（Depth Anything など）が出した法線・深度を絵に合わせて直す。寸法合わせ、ずれ（エッジの相互相関）、法線の流儀（OpenGL/DirectX を絵の明暗勾配との相関で判定して反転）、深度の向き（白が近いか遠いか）、ベクトルの正規化、狭い深度範囲の引き伸ばし。`map estimate` は設定ファイルに書いたコマンドを走らせてから import する（モデル本体はエンジンに入れない）。

**測定（正直な限界も含む）**
- 試作の生成法線は、実スキャンに対して「平らな法線」と同程度（cobble 14.2° vs 平ら 14.9°、brick 18.6° vs 18.1°、rock 9.1° vs 8.4°）。1 枚からの推定の限界で、**画質の主役は外部モデルの取り込み側**と考える。粗さの相関は cobble +0.64 だが brick −0.49（目地を逆に読む）。
- map import: 法線の流儀は cobble・rock で正しく判定、brick は「不明」で反転せず（安全側）。24px のずれを cobble・brick で回復、rock は 16px のみ（格子が粗い）。深度の 4 変種はすべて正解と一致（相関 1.0）。DirectX 法線 → import → PBR の流れでスキャンとの差 0.44°。
- 背景の穴埋め（pull-push）が GDScript で約 220ms。C++ 化で縮む見込み。

**提案（BACKLOG 登録のお願い。番号はリードに任せる）**
- P-1 `UZUPicture` ノード（C++）: JSON／Resource の仕様からメッシュ・素材・ライト・効果を組み立てる。シェーダーは試作の 2 本をそのまま出発点に。
- P-2 `UZUPBRFromImage`（C++ の静的 API ＋ ai_loop コマンド）: 試作の `pbr_tool.gd` の移植。種類ごとの値は試作の表を使う。
- P-3 `UZUMapImport`（同上）: 試作の `map_tool.gd` の移植。estimate は外部コマンドを呼ぶだけに留め、モデルは同梱しない。
- P-4 ai_loop のエージェントコマンド（analyze／snap／adopt／validate／shot）を既存の ai_loop の流儀に合わせる。
