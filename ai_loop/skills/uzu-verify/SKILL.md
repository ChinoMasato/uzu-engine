# uzu-verify: U.ZU プロジェクト／サンプル検証手順

U.ZU Engine でゲームサンプルやプロジェクト変更を検証するときは、単発の成功・数値だけで判断せず、以下の作法と手順に従って確認・報告する。

## 1. 検証の作法（チェックリスト）

検証に入る前・実施中・判定前に、以下を必ず確認する。

- **フレーム番号の一致**: ログや比較対象が指しているフレーム番号が、実際の実行フレーム（warmup 除外後など）と一致しているか確認する。
- **反復による再現性確認**: 1回だけの実行結果で合格・不合格を決めない。同じ条件（同一シード・同一シーン・同一引数）で繰り返して結果が安定しているか確かめる。
- **前回・基準との比較**: 変更前や既知のベースライン値と必ず並べて比較し、退行がないかを確認する。
- **処理速度は複数回計測**: パフォーマンスやフレーム時間は揺らぎが出るため、1回ではなく複数回測って傾向（平均・p95・最悪値）を見る。
- **fps だけで判断しない**: フレームレートや計測値が良くても、実際の見た目（スクリーンショットやレンダリング破綻の有無）と遊んだ感触（操作応答・当たり判定・テンポ）をあわせて確かめる。

## 2. 検証コマンド例

目的に応じて以下のコマンドを組み合わせて実行する。

- **完走検証（ゲームループ／プレイスルー）**
  対象サンプルディレクトリ配下の `verify_playthrough.py` を実行する。
  ```bash
  python3 <sample-dir>/verify_playthrough.py
  ```

- **UI 品質チェック**
  文字サイズ・はみ出し・余白・重なり・視認性を確認する。
  ```bash
  python3 ai_loop/uzu.py ui-quality <project-dir> <ui-scene>
  ```

- **音声・BGM/SFX チェック**
  配置時のクレジット台帳（ライセンス・出典記録）の整合と audio_check を確認する。
  ```bash
  python3 ai_loop/uzu.py audio_check <project-dir>
  ```
  あわせて、配置済み音声に対応するクレジット台帳の記載漏れ・形式不備がないか確認する。

- **フォント・ロケール対応チェック**
  UI やゲーム内テキストで使う文字がフォントに含まれているか確認する。
  ```bash
  python3 ai_loop/uzu.py font-locale-check <project-dir>
  ```

- **ai_loop 単体テスト全体**
  ```bash
  python3 -m unittest discover -s ai_loop/tests
  ```

## 3. 既知のベースライン（環境起因の失敗）

python3 -m unittest discover -s ai_loop/tests を実行した際、エンジンバイナリが不在の環境では test_animation の 4 件が失敗するという既知の環境起因ベースラインがある。

テスト失敗を見たら、まず失敗箇所が test_animation の既知 4 件（エンジンバイナリ不在起因）と一致するか照合する。

それ以外の失敗、またはバイナリが存在する環境での失敗は、新規の不具合または退行として調査する。

## 4. 報告の型

検証結果を報告するときは、検証条件と検証結果を明確に分け、推測や未実施事項を混ぜない。

```markdown
### 検証条件
- 使用バイナリ / コミット: （例: local build / HEAD、またはバイナリなし）
- 対象プロジェクト / サンプル: （パスやシーン名）
- 実行回数 / 計測条件: （例: 同一条件で 3 回実行、headless / render）

### 検証結果
- 完走検証: PASS / FAIL（要旨・差分）
- UI 品質 / 音・台帳 / フォント: PASS / FAIL（検知された項目）
- テスト (`ai_loop/tests`): PASS / 既知失敗のみ（test_animation 4件のみ等）/ FAIL
- 見た目・プレイ感: （確認内容と所見）

### 未確認項目
- （例: GPU レンダリング時の実機プレイ感、実バイナリ環境での test_animation 4件 など、未実施の項目を明記する）
```

## play-log の記録開始点（B-320）

- `play_log.Recorder` はラップ開始前のチェックポイント（ゲーム起動直後の "start" 等）を記録しない。完全なチェックポイント列が必要なら、ゲーム開始前に Recorder を生成し、開始前発火が 0 件なら `pre_start_events=0`、既発火があるならその件数を申告する。
- `play_log.summarize` の `pre_start_events`（整数、または未申告・旧形式なら None）と `checkpoints_complete`（0 のときだけ True）で、チェックポイント列の完全性を判別する。
