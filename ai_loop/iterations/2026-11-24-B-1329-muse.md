# B-1329 『スターホース牧場』U.ZU Engine 版サンプル（2026-11-24、Muse subagent）

Godot 製の同名ゲームとの比較用ミニ版を `ai_loop/samples/starhorse/` に作成。
ブランチ `agent/b-1329-muse`（基点 ai-native 375a886e22f）。

## 作ったもの

- **画面3つ**
  1. タイトル／牧場: ロゴ＋所有馬一覧。B-1326 の racing 世界観とキット部品
     （DataTable／DetailPanel／Chip／StatBar）を JSON spec（`specs/farm.json`、
     663行）から `uzu.py ui` で生成。行選択・フォーカスで詳細パネル連動。
     「レース登録」ボタンで出馬表へ。
  2. 出馬表: B-1326 見本の spec を土台に 8頭立てへ削減（`specs/entries.json`、
     549行）。枠色チップ・オッズ・人気つき。行選択で詳細連動、「レース映像」で
     レースへ、「戻る」で牧場へ。
  3. レース再生（`race.gd`、420行）: 2D 簡易シム。1800m 直線を枠色の
     勝負服＋馬番で走り、スピード／スタミナ／脚質（逃げ・先行・差し・追込）
     のペース配分＋疲労＋乱数で順位が決まる。カメラは先頭を追い、右に
     ライブ順位パネル、下に実況字幕。
- **音（Godot 版と同一素材）**
  - 実況29本（`audio/voice/`、README 対応表どおり）。局面イベント→
    ボイスのキュー再生は `commentary.gd`（115行）: Voice バス専用、
    終了信号＋長さウォッチドッグで送り、発火は全て `event_log` に記録。
    局面の選択はシムのスナップショット（600m／1200m 時点の順位、
    ゴール時の着差、勝ち馬の脚質・人気）から決める。
  - ファンファーレ（発走前）、BGM「The Hero's Journey」（牧場／出馬表で
    ループ、BGM バス −7dB）。バスレイアウトは `default_bus_layout.tres`。
- spec の生成元は `make_specs.py`（B-1326 見本 spec から派生させ、
  B-1328 の幅規則修正を引き継ぐ）。生成した `screens/*.tscn`（各約18MB）は
  B-1315 と同じ扱いでコミット対象外（`.gitignore`、spec から再生成）。

## 検証

- **ヘッドレス自動プレイ**（`verify_race.py`、固定シード1329・30倍速）: pass。
  8頭全馬完走（勝ち馬 ハヤテノツバサ 103.5秒）、実況19本が局面順に発火:
  01→02→03→04（好スタート）→07→08→09→10→11→12→13→14→17→18→
  20（押し切り）→23（逃げ切り）→27（6番人気の波乱）→28→29。
  レポートは `samples/starhorse/verify_report.json`。
- **撮影**（`capture.py`、Xvfb＋lavapipe）: `shots/farm.png`／`entries.png`／
  `race.png`。3画面とも目視確認済み（表の全列表示・詳細連動・字幕表示）。
- **audio-check**（`uzu.py audio-check`、29本個別）: 27/29 pass。
  残り2本（21_goal_close／29_closing）は文中の自然な間（無音 104ms／116ms、
  制限100ms）で fail。素材そのものの特性で、組み込み側の問題ではない。
- **全テスト**: 1606件中 1604 pass（fail は既知の [UDPServer] 2件のみ）。
  ※初回の build_locked 実行では UZUUI テスト1件が SIGTERM で落ちたが、
  同ケース単体（43件）とフル再実行で pass を確認済み——同時実行していた
  監視コマンドへの SIGTERM の巻き添えと判断。
- ビルド時の事故1件: 持ち込んだ .scons_cache に 0バイトのキャッシュ
  エントリがあり、main_timer_sync のオブジェクトが空になってリンク失敗。
  該当エントリとオブジェクトを削除して再ビルドし解消（コード側の問題ではない）。

## 比較所見

(a) **UIキットでの画面構築のしやすさ**: 2画面とも spec の JSON を書けば
表・詳細・チップ・バーが世界観つきで揃う。手間はほぼデータ（行と列）の
記述で、farm 663行・entries 549行の spec の大半は B-1326 見本からの
流用＋データ差し替え。配線（行選択→詳細、ボタン遷移）は main.gd 側
約60行。表の幅規則（uzu_ui.h 明記）があるので列幅で悩まない。
弱み: spec の DataTable に効くフォントサイズは theme 側だけ、等の
暗黙仕様は B-1328 の知見が前提になる。

(b) **音声の組み込みやすさ**: 実況キューは commentary.gd 115行で完結
（キュー＋バス分離＋ウォッチドッグ＋発火ログ）。局面→ボイスの対応は
race.gd 側の発火判定が本体で、スナップショット（順位・着差・脚質）を
持たせれば README の対応表どおりに機械的に書ける。発火ログを JSON で
検証できる形にしたのが大きく、音が出ないヘッドレス環境でも
「順序が正しい」ことを自動で示せた。

(c) **見た目**: 牧場・出馬表は B-1326 見本と同一水準（同じ spec・部品・
素材のため当然）。差はレース画面で、こちらは色矩形＋円の最小表現の
ため見本の作り込みには遠い——比較の主眼（UIキットと音）に対して
意図的に削った部分。実況字幕と順位パネルで情報の見え方は確保した。

(d) **動作の軽さ**: レース中の fps は lavapipe（ソフトウェア Vulkan、
1152×648）で平均 **31.8**（`shots/stats.json`、29サンプル）。2D 描画
のみの画面なのでソフトウェア描画でも実用域。ただし VM の実効1.5コア
での値で、GPU 環境では比較にならないほど軽いはず——数値は
「ソフトウェア描画でも破綻しない」の確認として読むこと。
プロジェクト容量は生成物を除いて約11MB（うち音素材 8.8MB が大半、
WAV 29本＋MP3 2本）。生成画面シーン（各約18MB）はコミット対象外。

## 残差分・申し送り

- レース画面の馬は矩形＋円の簡易表現（3D 化・スプライト化は範囲外）。
- 実況の 15（外から）／16（内を突いて）は 1200m 時点の先頭馬の順位で
  判定する近似。勝ち馬確定後に選ぶ方式にすれば精度は上がるが、
  実況の同時性（直線途中で流れる）を優先した。
- BGM／ファンファーレは MP3 のため audio-check の対象外（WAV 専用）。
- 21／29 の無音超過は素材側の特性として記録のみ（トリムは Godot 版との
  同一素材という前提を崩すため行わない）。
