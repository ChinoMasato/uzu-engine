## 繰り返し指数の測り方の変更と根拠

旧経路（スクリーンショット上の自己相関）は2つの意味で壊れていた:
1. **振幅盲目**: 相関は振幅を見ない。実測では wafu の滑らかな羊皮紙が 0.7319、
   persona が 0.9104 と両方 fail になり、「見える繰り返し」と測っている量が
   対応していなかった。
2. **測定対象の混線**: 画面全体で測ると UI 配置の周期性まで拾う。

新経路（texture_repetition_sheet）: テクスチャ単体を空パネルシートとして
ネイティブ解像度で描き、中央最大 512×512 を測る。
- **パターン経路**（軸ごとに周期検出: 局所最大＋A(d)≥0.5＋2倍ラグでも ≥0.5 の
  櫛条件＋谷から 0.15 以上の再興、周期上限 24px）: 設計された均一パターンは
  「周期で折り返した予測からの偏差（残差）」≤0.30 とセル均一性
  （周期セル平均の広がり/チャネルスケール ≤0.6）で判定する。周期性そのものは
  合否にしない。
- **非パターン経路**: 可視性指数 V＝band_peak×min(1, std/20) ≤0.30。自己相関は
  振幅を見ないが知覚は振幅に比例する、というのが重みの根拠。
- 実測: persona の TILE_FIT シートは残差 **1.58 で fail**（リスケールがドット
  格子と干渉するモアレを正しく検出）、TILE ネイティブ描画は残差 **0.072 で pass**
  （周期 [8,8]、均一性 0.106）。wafu は可視性 **0.058 で pass**。
  → この fail が halftone の TILE 化（キット修正）の根拠になった。閾値 0.30 は
  変更していない。

被覆率（texture_coverage）の判定変更: 当初 α≥0.999 としたが sf（0.839）／
default（0.894）のガラスパネル（意図的な半透明）を誤検出した。「穴＝局所的な
崩落」として **alpha_min ≥ 0.5×alpha_mean** に変更: 楔（min 0）は fail、
ガラス（均一な半透明）は pass、という区別が監査の意図（B-1318 の楔抜け検出）に合う。

スライダー溝ソルバーのバグと修正: 当初ソルバーは「オプション色のパネル色」に
対して解いたため fantasy 1.594／sf 1.989 で fail した。ゲートが測るのは描画済み
テクスチャの中心画素なので、stylebox_center_color() で実測中心色を渡すよう
両呼び出し側を修正し、全テーマ pass になった。「解く相手は宣言値でなく実測値」
が教訓。

## 包含ルール（オーナー追加要件）への対応

1. 包含ルール: ゲート項目 containment として機械化（上記プローブ）。静止時＋
   モーション peak の両方で測る。
2. value_change: 充填 100% クランプ＋超過は明るさ／スケール表現へ（上記）。
   既存テストの固定は表現変更に合わせて更新（理由は変更ファイル節に明記）。
3. skew セーフエリア: キットに `UZUUI.get_skew_safe_margins()` を新設
   （slope 0.25、persona travel=79.0）。行別モデル: 左 inset＝travel×(部品の
   最下行 fraction)、右 inset＝travel×(1−最上行 fraction)。見本側は Margin で
   担保した。**不足として記録**: ui_tool の JSON 配置時に skew を見て自動で
   Margin を挟む機能は未実装（見本側レイアウトで担保する現行運用で足りるかは
   次の見本作成時に再評価）。
   なお包含プローブ側の境界は API の travel ではなく、スタイルボックスの
   テクスチャ実走査（persona 左端: 最上行 13px → 最下行 85px、travel 72 over
   形状高 291px、傾斜 0.247 ≈ 設計 0.25 と一致）で測る。API は設計時の見積もり、
   ゲートは実測、という役割分担。
4. 機械チェック: ui_quality.py の check_containment（JSON 項目 containment）。
   ゲート全項目 pass に含む。
5. 撮影確認: persona 5画面すべてで「はみ出しなし・見切れなし」を目視確認し、
   チェックリストに包含の行を追加した（下記チェックリスト最終行）。

当初プローブの測定バグ2件（記録として残す）: ① Control の rect を
get_global_transform に掛ける際に position を二重加算していた（子が深いほど
誤差が増えた）。② 斜行境界を content margin 起点でモデル化していた（実際は
テクスチャ形状そのものが境界）。どちらも実測（テクスチャ走査）でモデルを
確定させてから直した。

## 失敗履歴

- doctest が CHECK 内の `&&` を禁止 → アサーションを分割。
- `MOUSE_BUTTON_LEFT` は GDScript 名であり C++ では未宣言 →
  `MouseButton::LEFT`（core/input/input_enums.h）＋include 追加。
- Theme の variation 名に実クラス名 UZUTouchStick は使えない
  （theme.cpp:1409 のエラー: 実クラス名と同名の variation は不可）→ variation
  登録を削除し、色はクラス名の下に置く方式に変更。これが「スティックは実クラス、
  ボタンは variation」という非対称の理由。
- VM 交換でビルドが2回死亡（/tmp のログ喪失、プロセス消滅）。worktree と
  bin/obj は永続し、scons は増分再開できた。
- 包含プローブの測定バグ2件（上記「包含ルール」節）。
- スライダー溝ソルバーの「宣言値で解く」バグ（上記）。

「包含プローブで実測して確定」は成り立っていなかった。原因は2段:

1. **screens/*.tscn が古かった**: 会話窓マージン 64 のキット修正より
   前に生成されており、修正が焼き込まれていなかった。全10画面を現行
   バイナリで再生成すると Next と Line 左は解消し、Line 右 4.5px のみ
   残った。tscn はテーマを焼き込むため、キット修正後は再生成が必須。
2. **平坦な左右マージンでは右上の斜行に足りない**: テクスチャ実走査で
   は、平行四辺形の右境界は最上行で内側 74px（左右マージンの上限 64
   を超過）。本文行の上端の行では 68.5px 要る。対策として UZUTalk の
   skew 対応に**上マージン 32**（余白スケール内）を追加し、本文ブロッ
   クの開始行そのものを下げた（行別 inset の垂直方向の等価変換）。
   テストで L64／R64／T32 を固定。実寸（幅 1056）でもプローブと同モ
   デルで pass を別途確認した。

撮影の目視で見つけた persona の見切れ2件もキット側で修正:

3. **名前タグの崩れ**: UZUNameTag が skew フレームを継承していたが、
   タグ実寸 65×37 に対し九分割マージンが左右 90／上下 26（合計が実寸
   超過）で、本体が細片に潰れ、話者名がタグの外に半分出ていた。
   リボンと同じ規約で、skew のときタグは chamfer に落とす（テストで
   スライスの一様性を固定）。
4. **OptionButton のラベル**: 左寄せラベルが skew の左上の切り欠きに
   かかり、境界線が文字を横切っていた。skew 世界観では OptionButton
   の左 content margin を 64 に広げ、ラベルを形状内に収めた（48 では
   境界の実測位置 ≈58px に届かず不足。テストで固定）。中央寄せの
   Button は対象外。

**B-1318 の残存制限の閾値訂正**: 「中央帯 512px 超の背の高い skew
パネルで段差」とあったが、実測では中央帯がタイル1枚分（256px）を
超えると側ストリップの縦タイリング継ぎ目で輪郭に段差が出る
（persona menu／settings の撮影で確認、パネル高 452 で1段）。内容の
包含・ゲートには影響しない。根本対策（skew 専用に中央帯を2倍高で
生成する等）は本項目の範囲外として、リードへの申し送りに留める。
