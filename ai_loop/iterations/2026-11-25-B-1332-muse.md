# B-1332 『スターホース牧場』レースの3D化（2026-11-25、担当 muse）

千野の判定「ChatGPT で出した絵をつなげるだけだと画面の構造として
破綻している箇所だらけ」「基本的には3Dで構築した方が良い」を受け、
B-1330 のレース画面（横視点 2.5D の貼り合わせ）を実3Dシーンに
差し替えた。差し替えはレースのみで、タイトル／牧場／出馬表／結果の
2D 画面、シム（脚質・疲労・順位決定）、実況同期（commentary.gd）、
画面遷移は B-1330 をそのまま継承。エンジン／キット側のコードは
無変更（差分は ai_loop/samples/starhorse/ と CLAIMS のみ）。

## 使った素材（すべてプロジェクト内 models/ に取り込み済み）

- 馬: horse-assets/horse-rigged.glb（10.5MB、リグ済み、Gallop
  アニメーション 0.708 秒、17 関節、約60k tris）。向きは +Z、
  全長 1.0 ユニット、足元は原点の -0.404。毛色は鹿毛＋白斑で
  鞍は描き込み済み。
- ジョッキー: horse-assets/jockey-seated.glb（4.7MB、騎乗姿勢の
  静的メッシュ、原点は骨盤＝座面、約40k tris）。
- 競馬場: ts-spaces/dabisutamitainajing-ma-gemu/assets/ の
  grandstand.glb（スタンド、長さ11・高さ約5.9m）、
  starting_gate.glb（4枠ユニット、枠ピッチ1.15m）、
  racecourse_props.glb（ゴールポスト、ラチ、木、生垣、距離標識）。
- 軽量版 GLB（horse-rigged-web.glb 等）は KHR_mesh_quantization＋
  EXT_texture_webp 必須で、この Godot ビルドでは読み込めないことを
  実測で確認したため不採用（GLTFDocument が ERR_PARSE_ERROR）。
  非量子化版を8頭で共有し、総ポリゴン・メモリを抑えた。

## 作ったもの（race.gd 全面書き換え、約900行）

- **3D ワールド**: SubViewport（own_world_3d）の中に Node3D を構築
  し、HUD（順位・残り距離・字幕・進捗・フラッシュ）は従来どおり
  Control で上に重ねる。main.gd ルートの全面 ColorRect がルートの
  3D を塗りつぶす問題を SubViewport 方式で回避し、画面遷移
  （UZUUIJuice.transition）も Control 単位で効く形を維持。
- **コース**: 直線 1800m。基底地面＋芝ストリップを 60m 帯の
  モーイングストライプ（2色交互）で構築、ゴールライン、far 側に
  ヘッジ帯。ラチは props のポスト／バーを MultiMesh 化（両側、
  4m 間隔）。距離標識は 200m ごとに props を複製＋残り距離の
  Label3D。ゴールポスト一式、スタンド（×2.2、ゴール側4基＋
  スタート側2基）、木・生垣（決定的配置、seed 7）。ゲートは
  starting_gate を2基並べ、枠中心がレーンと一致する配置
  （レーン間隔 1.15m ＝ ゲートの枠ピッチ）。
- **馬8頭**: root（rotation.y=π/2 で +Z 向きモデルを +X 進行に
  変換）→ mount（scale 2.3）→ 馬インスタンス（足裏が mount 原点に
  一致するよう y オフセット）。毛色は馬ごとに COATS 8色の
  albedo ティント（素材を複製して surface override）、勝負服は
  枠ごとに SILKS 8色。ジョッキーとゼッケンは BoneAttachment3D
  （bone="spine"）の子にし、子変換は rest の逆行列×目標変換で
  設定（ジョッキーは馬ローカル (0, 0.27, -0.03)）。ゼッケンは
  枠色の薄いボックス＋両側面に枠番号 Label3D。馬名タグは
  billboard Label3D を頭上に。
- **ギャロップの実現方法**: GLB 内蔵の Gallop アニメーションを
  AnimationPlayer で再生し、speed_scale を地面速度に同期させた
  （vel × slowmo × time_scale / 8.5、0〜3 にクランプ。歩幅約6m
  一定）。スローモーション時に脚だけ速くならないよう slowmo と
  time_scale を含めるのが要。発走前は停止＋reset_bone_poses で
  ゲート内に静止。土煙は CPUParticles3D（馬ごと、速度6超で放出、
  local_coords=false で流れを残す）。
- **カメラ**: 競馬中継型。発走前はゲート正面寄り、レース中は
  先頭追従（focus-3.0 から focus+8.0 を注視）、残り400mから
  z 16.5→11.0・y 2.8→2.25 に寄せ、ゴール後は勝ち馬にフォーカス。
  平滑化はレース時間 dt 基準の exp 減衰（time_scale で早送り
  してもパンが遅れないよう、実時間でなくシム時間で平滑化する）。
- **環境**: ProceduralSkyMaterial の空、ACES トーンマップ、
  露出 1.05、指数フォグ（density 0.0011）、DirectionalLight
  （影オン、最大距離170）＋逆方向のフィル光。

## 検証

- 自動プレイ verify_race.py: pass（8頭完走、勝ち馬ハヤテノツバサ
  ＝B-1330 と同一シム結果、実況19本が局面順に発火、problems なし）。
  カメラ平滑化の修正後も再 pass を確認。
- デバッグ撮影（capture.py、Xvfb＋lavapipe）: 中盤の撮影で8頭の
  疾走・ジョッキーの騎乗位置・ゼッケン番号・馬名タグ・土煙・
  スタンド・ゲート・ゴールポスト・ラチ・ストライプを目視確認。
  スタート直後の撮影でカメラの追従遅れ（早送り時にパンが実時間
  基準で遅れる）を発見し、上記のシム時間基準への修正で対処した。
- 全テスト: 自 worktree のビルド（editor, tests=yes）で
  1604/1606 pass。失敗2件は既知の環境起因 [UDPServer] 2件のみ
  （無変更バイナリでも再現するもの）。
- Windows exe: B-1330 で作り直した新テンプレートで書き出し
  rc=0・SCRIPT ERROR なし。starhorse.exe 81,261,568 バイト＋
  starhorse.pck 53,265,836 バイト（PCK 内に models/ の5つの
  GLB が含まれることを確認）。zip は
  ~/workspace/your_files/starhorse-uzu-win.zip を差し替え
  （73,301,796 バイト）。Windows 実機での起動は未検証
  （エディタバイナリでの起動・完走は検証済み）。

## 途中で直した不具合

- CPUParticles3D に draw_pass_1 は無い（GPUParticles3D の
  プロパティ）。mesh プロパティへの代入に修正。修正前は
  _build_runners が途中で落ちてレースが始まらなかった。
- 土煙が真っ黒に描画された: 支給 dust.png は RGB が全て0の
  アルファ専用マスクで、3D ビルボードでは黒い塊になる。
  コード生成の放射グラデーション（白 RGB＋α減衰）に差し替え。
- 画面生成物 screens/*.tscn は gitignore 対象（specs から
  uzu.py ui で生成）。新 worktree では生成し直しが必要で、
  キャプチャ／書き出しの前に3画面分を生成した。

## 残った限界（正直な記録）

- ゲート扉の開閉アニメーションは未実装（扉ノードの原点が中心で
  ヒンジ回転できないため見送り）。発走は馬がそのまま出る形。
- ジョッキーの勝負服ティントは素材の複製マテリアル全体にかかる
  ため、肌色も一緒に色がずれる。控えめな範囲に留めた。
- 馬の実 GPU での見え方・速度は VM（lavapipe）では未計測。
  最終確認は千野の exe で行う前提。
- スタンド・プロップは支給 GLB の作りをそのまま使い、ゴール側に
  寄せて配置した。観客等の作り込みはしていない。
- 影は DirectionalLight の範囲 170m に限定。カメラ付近では
  問題ないが、コース全域を同時に見渡す画では遠方が無影になる。
