## 2. プロジェクト概要

- **U.ZU Engine** は、ゲームエンジン Godot のフォークとして開発する AI ネイティブな新エンジン。
- **位置づけ（2026-11-19 オーナーの見方）**: U.ZU Engine は単独で完結する製品というより、**AI エージェントから呼び出される「ゲームを作る道具」の一つ**である。Blender（モデル）、画像生成（テクスチャ）、DAW（音）など他の道具と並んでエージェントに使われ、その中で U.ZU の固有価値は「作る→公開→遊ばれる→感想が戻る→直す」の検証サイクルを回す道具であること。だからこそ全機能を AI から呼べる形（CLI／MCP／構造化出力）で出し、カタログ（B-403）で発見可能にし、エージェントの能力に適応する（B-404）。
さらに、道具群が一つのツールにまとまっている必要もない（2026-11-19 オーナー）。道具ごとに独立して呼べる形を保ち、エージェントが選んで組み合わせる前提で設計する（B-405）。
言い換えれば U.ZU は **AI がゲームを作るための手足群**である（2026-11-19 オーナー）。頭脳はエージェント、手足は道具。手足には感覚が要る — 構造化出力・スクリーンショット・数値指標は手足の固有感覚に当たり、「やったこと」と「結果どうなったか」が返らない道具は頭脳に使われなくなる。道具の設計では、実行とフィードバックを必ずセットにする。

- **イメージ先行フロー（2026-11-20 オーナー指示）**: AI 開発では、AI が生成したイメージイラストからゲームを作っていく流れが適している。イラストは「完成形の仕様書」として働く — 見た目の正解が先に固定され、テキスト仕様より曖昧さが少なく、人間の承認も1枚で速い。工程は、イラスト生成 → レイヤー分離と深度でシーン雛形を起こす（B-1221）→ ロジックを付けて育てる → スクリーンショットと元イラストの差分で検証する。2.5D の戦略（B-1216）もこの流れの一部である。
- ベース: 本家 godotengine/godot の master、**フォーク点コミット `203bf0a23fd7d90a860917e66de08e20d2596244`**（Godot 4.8.0 beta）。ライセンスは MIT。
- 開発ブランチ: **`ai-native`**。フォーク点の上に運用コミットが積まれている（プロジェクト開始／命名／Phase 3・5・6 バックログ／橋 API／マルチエージェント基盤／本ブリーフィング。履歴は `git log` で確認）。

## 3. 憲法 — このエンジンの目的（オーナーの言葉）

> **「面白いゲームを作るためのエンジン。今までのゲームエンジンは作るで終わっていた」**

今までのエンジンは「作る」で終わっていた。U.ZU Engine はその先 — 公開する、遊ばれる、感想が戻る、直す — までをエンジンの仕事に含める。

```
作る → プロトタイプを公開する → 遊ばれる（人＋AIプレイヤー）
→ 詰まり・離脱・感想が構造化されて戻る → 直す → また公開する
```

- 評価軸は制作効率ではなく、**この検証サイクルの回転数**。全機能の採否は「サイクルを速くするか、感想を具体的にするか」で判断する。
- 面白さ自体は測れない。測れるのは代理指標（詰まり率、離脱点、リプレイ、感想の量と具体性）まで。エンジンは収集と提示を担い、判断は人間が持つ。

## 4. 製品構成 — U.ZU Engine × Gogashare（決定済み）

Roblox の Studio／Player のように、制作側とプレイ側を**別プロダクトに分離**する。

| | U.ZU Engine（制作側） | Gogashare（プレイ側） |
|---|---|---|
| 役割 | 作る道具。エディタ、AI 開発ループ、書き出し | 遊ぶ・感想を返す・集まる場所（ユーズ社の既存事業） |
| 進化 | 遅く・安定。上流追随が律速 | 速く・実験的（Web サービス） |
| 形態 | Godot フォーク（MIT） | U.ZU クラウドのサービス |

- エンジン側に持つのは**「橋」だけ**： ①1コマンド公開（書き出し→アップロード） ②戻ってきた感想・テレメトリを読むビュー ③試遊会への参加口。境界は API 契約として固定する（バックログ B-503）。コミュニティ機能の本体はエンジンに入れない。
- 分離の理由： 進化速度の衝突回避（コミュニティの実験が授業で使うツールの安定性を脅かさない）、遊ぶ人の導入障壁を下げる（ブラウザで即プレイ）、MIT フォークと事業サービスの分離。

## 5. 場所の思想（Gogashare 側の設計原則）

- **「売る場所ではなく、ゲームを作って楽しむ場所」**。ストア、売上ランキング、課金導線はコアに持たない。収益はサービス側（サポート／クラウド／教育）で取る。
- 報酬設計の核は **「遊んで感想もらえるだけで嬉しい」**。作者に届ける主役の数字は「遊んでくれた人数」と「感想の到着」。発見の仕組みは「まだ誰にも遊ばれていないプロトタイプに最初の1人を届ける」ことを最優先にする。
- 参照モデルはライバーアプリ（SHOWROOM 型）： ルームの文化（クラス／ジャム／チーム＝「渦」がルーム）、反応の即時性（作者在室の試遊会、遊ぶ様子の観戦）、応援し見届ける楽しさ、素人の舞台。**ただし投げ銭・ギフト経済とランキング競争は持ち込まない**（「ライブ感と応援文化は借りるが、経済と競争は借りない」）。
- 感想は点数化しない（星評価なし）。構造化するのは詰まり／バグ／アイデアという「直すための情報」だけで、感想の本文は贈り物としてそのまま作者に届ける。
- 公開の単位は完成品ではなく**プロトタイプ**。作りかけを出すのが標準。

## 6. 開発方法論 — 検証ループ（絶対の手順）

エンジン本体の改善は、次のループでのみ行います。

```
課題を1件選ぶ → 修正＋テストを書く → 増分ビルド → 単体テスト全件実行
→ 全 pass なら採用して commit ／ 1件でも fail なら差し戻し → 台帳に記録
```

- 1イテレーション = 1課題。diff は小さく保つ。ついでのリファクタリングや整形はしない。
- テスト／ベンチマークで機械判定できない変更はループに入れない（描画の見た目など人間の判断が要る領域は対象外）。
- 設計判断（アーキテクチャ、公開 API の形）はオーナーの承認なしに変えない。

### マルチエージェント規則（要約。詳細は `ai_loop/MULTI_AGENT.md`）

- **1エージェント = 1 BACKLOG項目 = 1 git worktree + 専用ブランチ** `agent/<項目ID小文字>-<担当名>`。メインチェックアウト（ai-native）で直接編集しない。worktree は `ai_loop/agent_start.sh <項目ID> <名前>` で作る。
- 着手前に `ai_loop/CLAIMS.md` へ担当と触るパスを宣言する。所有権はサブシステム単位（core/、scene/、servers/、drivers/、modules/<名>/、editor/、platform/、tests/）で分ける。
- 共有ファイル（`version.py`、`SConstruct`、プロジェクト形式の中核、`ai_loop/` の運用ファイル）は統合担当（リード）だけが触る。
- ビルドは `ai_loop/build_locked.sh` 経由で直列化する（flock）。仕上げは `ai_loop/agent_finish.sh`（ビルド＋全テスト）。
- 記録は `ai_loop/iterations/<日付>-<項目ID>-<担当名>.md` に1ファイルで残す。`ai-native` へのマージと `ai_loop/LEDGER.md` への追記はリードだけが行う。

### ハードルール

- **本家 Godot リポジトリへは絶対に PR・提出しない**（本家の貢献ポリシーが AI 生成コードを禁じているため。このフォークの成果はフォーク内に留める）。
- `thirdparty/` は原則変更禁止（バージョン更新はオーナー承認時のみ）。
- プロジェクト形式の互換を壊さない（.tscn／.gd／.tres／project.godot）。
- MIT の著作権・ライセンス表記を維持する。商品名に「Godot」を使わない（エンジン名は U.ZU Engine。「Godot ベース」という事実記載は可）。
- 上流のコードスタイル（clang-format、GDScript スタイルガイド）に従う。

## 7. ビルドとテスト

```sh
# ビルド（template_release、単体テスト入り）
scons platform=linuxbsd target=template_release tests=yes accesskit=no arch=x86_64 -j3
# 並行開発時は ai_loop/build_locked.sh を使うこと（SCONS 環境変数で scons のパスを指定可）

# 単体テスト（doctest）
bin/godot.linuxbsd.template_release.x86_64 --test

# バージョン確認
bin/godot.linuxbsd.template_release.x86_64 --version
```

- フルビルドは環境により1〜1.5時間規模。以後は増分ビルドが通常のループ。
- 採用条件は「単体テスト全件 pass」。fail があれば差し戻し、台帳に理由を残す。

## 道具はゲームを作りながら磨く（2026-11-20 オーナー原則）

道具は単体で作っても役に立つものにならない。サンプルゲームを実際に作る過程で初めて不便が見え、道具が磨かれる。新しい道具には原則として実証用のサンプルでの使用をセットにし、サンプル側で見つけた不便・不足は道具側の改善として BACKLOG に還す（『灯りの欠片』が UZUJuice・世界観 UI・マップ生成の実証と改善の場になったのが前例）。

## UI の原則（2026-11-22 オーナーの言葉）

「ゲームは UI でクオリティの大半が決まります」「ゲーム自体がリッチな UI ともいえる」。UI は後付けの体裁ではなく、ゲームの品質そのもの。メニューや HUD だけでなく、ゲーム画面そのもの（描画の豊かさ、演出、触って返ってくる反応）がプレイヤーにとってのインターフェースである。したがって UI キット（UZUUI）の品質はエンジンの中心品質であり、品質ゲート（B-1310）で数値基準を持ち、AAA 水準を要求する。画面側の豊かさ（2.5D・イメージ先行・juice）も同じ UI 品質の一部として扱う。

## 事前計算の原則（2026-11-21 オーナー方針）

入力が決まれば結果が決まる静的な計算は、実行時ではなく開発時に計算してデータとして同梱する（ナビメッシュのベイク、生成結果、焼き込み済みライティング等）。実行時の生成・ベイクは「入力が変わる場合のフォールバック」と位置づける。例外は容量を小さく保たなければならない場合（Web 配布など）のみで、その場合は容量と起動コストのトレードオフを明示して判断する。前例: 『灯りの欠片』のナビメッシュベイクはシード固定の決定的生成ゆえ事前計算可能で、開始時のひっかかりの主因だった（2026-11-21 オーナー指摘）。

## 双方向の原則——エンジンがAIへプロンプトを返す（2026-11-24 オーナー方針）

AI がエンジンを呼び出すのが一方向ではない。逆もある：**エンジンが「実行してほしいプロンプト」を返し、AI がそれを実行して、結果をエンジンへ返す**。

- エンジンに無い能力（画像生成、文章の生成、出来栄えの評価判断など）が要る場面では、エンジンは構造化されたプロンプト要求（種類／プロンプト全文／期待する結果の形式／ID）を返し、実行は AI 側に委ねる。結果が戻ればエンジンは処理を続ける。
- プロンプトの組み立ては機械的な仕事なので、エンジン側の仕組みが担う。アイデア組み合わせページ（要素×テンプレート→プロンプト全文）のように、仕組みから連携プロンプトを決定的に組み立てて返す。AI は要約・改変せず全文を実行する（要約すると条件が抜ける）。
- 能力プロファイル（B-404）と対になる原則：エンジンは「相手の AI が何をできるか」を知って道具の出し方を変えるだけでなく、「自分にできないこと」をプロンプトとして相手に依頼できる。
